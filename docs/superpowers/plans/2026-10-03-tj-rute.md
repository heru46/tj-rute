# TJ Rute Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Webapp mobile statis yang memberi panduan rute Transjakarta dari titik A ke B.

**Architecture:** Script Node mengubah GTFS resmi menjadi `data/network.json` + `data/shapes.json`. Browser memuat data itu, menghitung rute dengan RAPTOR berbasis frekuensi (`src/router.js`, murni tanpa DOM), lalu menampilkan hasil di Leaflet + bottom sheet. PWA dengan service worker.

**Tech Stack:** HTML/CSS/JS ES module tanpa framework, Leaflet 1.9.4 (vendored), Node 22 (`node:test`; zip diekstrak dengan `tar` bawaan sistem), Photon geocoder, tile CARTO Voyager.

**Spec:** `docs/superpowers/specs/2026-10-03-tj-rute-design.md`

## Global Constraints

- Tanpa server sendiri; semua file statis, siap GitHub Pages.
- Semua kategori `route_desc` ikut dihitung.
- Akses/egress jalan kaki ≤ 1.000 m; transfer jalan kaki ≤ 400 m; faktor jalan 1,3; kecepatan 1,25 m/s.
- Penalti transfer 120 s; maksimum 4 kendaraan; maksimum 5 itinerary.
- Tunggu = headway ÷ 2 di dalam jendela frekuensi.
- Teks UI berbahasa Indonesia.
- Bbox Photon: `106.4,-6.75,107.2,-6.0`.

## Perubahan terhadap spec

- Transfer jalan kaki ≤ 400 m dihitung di browser saat data dimuat (grid spasial), bukan saat build, supaya `network.json` tidak membengkak ~1,5 MB oleh pasangan halte. `transfers.txt` tetap disimpan di JSON.

## Format data (kontrak antar-task)

`data/network.json`:

```json
{
  "generated": "2026-10-03T00:00:00Z",
  "source": "https://gtfs.transjakarta.co.id/files/file_gtfs.zip",
  "stops": { "id": ["B00001P"], "name": ["18 Office Park"], "lat": [-6.299146], "lon": [106.8321] },
  "routes": [{ "id": "1", "short": "1", "long": "Blok M - Kota", "cat": "BRT", "color": "D7262D", "text": "FFFFFF", "fare": "FP" }],
  "fares": { "FP": { "price": 3500, "transferSec": 10800 } },
  "services": { "SH": { "days": "1111111", "start": 20040115, "end": 20271231 } },
  "patterns": [{ "route": 0, "head": "Kota", "svc": "SH", "shape": "1-R01_shp", "stops": [0, 5], "t": [0, 180], "freq": [[18000, 79200, 300]] }],
  "transfers": [[0, 5]]
}
```

Semua referensi halte/rute memakai indeks array. `t` dan `freq` dalam detik sejak 00:00.

`data/shapes.json`: `{ "<shape_id>": "<encoded polyline presisi 5>" }`.

Itinerary (keluaran router):

```js
{
  departSec, arriveSec, rides, walkMeters,
  legs: [
    { type: 'walk', from: Point, to: Point, sec, meters },
    { type: 'ride', pattern, route, fromStop, toStop, fromPos, toPos, waitSec, boardSec, alightSec }
  ]
}
// Point = { lat, lon, name, stop? }
```

### Task 2: Router RAPTOR

**Files:**
- Create: `src/geo.js`, `src/router.js`, `test/router.test.mjs`

**Interfaces:**
- `geo.haversine(aLat, aLon, bLat, bLon) → meters`; `geo.walkSec(meters) → seconds` (meters × 1,3 ÷ 1,25, dibulatkan).
- `router.prepare(network) → Index` (grid halte, stopPatterns, footpaths ≤ 400 m + transfers GTFS, rute aktif per hari).
- `router.plan(index, { from: Point, to: Point, departSec, date: Date, excludeRoutes?: Set<number> }) → Itinerary[]` (hasil Pareto per jumlah kendaraan).
- `router.planAlternatives(index, query, max = 5) → Itinerary[]` — jalankan `plan`, lalu ulangi dengan mengecualikan tiap rute dari hasil terbaik, buang duplikat (kunci = urutan rute), urutkan `arriveSec` lalu `rides`.
- `router.nearbyStops(index, lat, lon, maxMeters) → [{ stop, meters }]`.

Fixture tes: jaringan buatan 6 halte dalam garis lurus (jarak ±500 m antar-halte, longitude bertambah 0,0045), rute A (halte 0→1→2, headway 600 s, 05:00–22:00), rute B (halte 2→3→4, headway 300 s), rute C khusus Minggu (svc `HM`) 0→4, halte 5 terisolasi.

- [ ] Step 1: Tes:
  - naik langsung: dari titik di halte 0 ke halte 2 pukul 08:00 → 1 ride rute A, `waitSec === 300`, tiba = 08:00 + 300 + offset.
  - transfer: halte 0 → halte 4 hari Senin → 2 ride (A lalu B), tunggu kedua 150 s + penalti 120 s.
  - hari layanan: halte 0 → halte 4 hari Minggu → ada opsi 1 ride rute C.
  - jendela tutup: berangkat 22:30 → tidak ada itinerary.
  - sebelum jendela: berangkat 04:50 → naik saat jendela buka 05:00 (tunggu 600 s).
  - akses > 1 km: dari titik 2 km dari semua halte → `[]`.
  - jalan kaki saja: A–B 600 m → itinerary satu leg walk.
  - `excludeRoutes` berisi A → tidak ada hasil memakai A.
- [ ] Step 2: `node --test test/router.test.mjs` → FAIL (modul belum ada).
- [ ] Step 3: Implement RAPTOR:
  - Ronde 0: label halte akses = depart + walkSec(jarak).
  - Ronde k (1..4): untuk tiap pola yang menyentuh halte bertanda, telusuri dari posisi bertanda paling awal. Kunci trip = `depart - t[pos]`; naik di posisi p bila `labelPrev[p] + tunggu(p) - t[p]` lebih kecil dari kunci sekarang. Tunggu: cari jendela `[s,e,h]` dengan `s ≤ x < e` (x = label − t[p]) → h/2; bila x < s jendela berikutnya → s − x; selain itu tidak bisa naik. Ronde ≥ 2 menambah penalti 120 s ke tunggu.
  - Setelah scan, relaksasi footpath dari halte yang membaik (tanpa berantai).
  - Simpan parent per ronde untuk rekonstruksi.
  - Tujuan: `label_k[s] + walkSec(egress)`; simpan hanya bila lebih baik dari ronde sebelumnya.
- [ ] Step 4: Tes PASS.
- [ ] Step 5: Commit `feat: router RAPTOR berbasis frekuensi`.
